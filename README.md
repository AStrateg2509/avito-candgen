# Кандидатогенерация для поиска услуг Авито

Человек ищет услугу — «ремонт холодильника», «репетитор по математике» — в своём городе, иногда с фильтром по виду услуги. Для каждого из 2 452 таких запросов нужно отобрать из 189 тысяч объявлений 50 кандидатов так, чтобы среди них оказались объявления, которые человек действительно выбрал. Качество измеряется метрикой Recall@50 — долей нужных объявлений, попавших в эти 50.

**Результат на лидерборде: Recall@50 = 0,8963.** Решение работает офлайн на одной видеокарте 8 ГБ и воспроизводится одной командой.

## Как устроено решение

```mermaid
flowchart LR
    T["train.parquet"] --> FT["дообучение e5-small: MNRL, hard negatives той же локации и подкатегории"]
    T --> PLOC["P(loc_item | loc_search): матрица переходов"]
    T --> PMC["P_mc: kNN по текстам запросов"]
    I["benchmark_items.parquet"] --> DOC["текст: заголовок x2 + параметры без шума + описание"]
    DOC --> CHAR["char_wb 3-5 TF-IDF"]
    DOC --> WORD["word 1-2 TF-IDF по леммам"]
    I --> DDOC["dense-документ: заголовок + параметры 300 + описание 700"]
    DDOC --> DENSE["эмбеддинги e5-small ftd, 256 токенов"]
    FT --> DENSE
    Q["benchmark_queries.parquet"] --> FIL["фильтр: Вид и Тип услуги"]
    CHAR --> LIN["линейный скор по всему корпусу, батчи на GPU"]
    WORD --> LIN
    DENSE --> LIN
    PLOC --> LIN
    PMC --> LIN
    FIL --> LIN
    LIN --> POOL["пул: top-100 четырёх каналов, ~175 кандидатов"]
    POOL --> RANK["LGBMRanker lambdarank, 30 признаков, обучен на холодной валидации"]
    RANK --> ANS["answer.csv: top-50 + валидатор формата"]
```

Каждое объявление корпуса получает оценку, в которой сложены похожесть текста и то, насколько вероятны для этого запроса локация, подкатегория и значение фильтра. Из лучших по нескольким таким оценкам собирается пул примерно из 175 кандидатов, и обученная модель выбирает из него итоговые 50.

## Кратко по пунктам

### Какие данные и признаки использованы и почему

**Данные:**
- **`train.parquet`** — около 498 тысяч кликов: текст, локация и фильтр поиска, выбранное объявление, его локация и подкатегория. Отсюда берутся вероятности локации и подкатегории, пары для дообучения модели текста, отложенная валидация и разметка для ранкера.
- **`benchmark_items.parquet`** — 189 тысяч объявлений. Заголовок, параметры и описание нужны для сравнения текстов, локация и её координаты — для вероятности локации и расстояния. Ещё используются подкатегория, цена и флаги объявления (скрыт телефон, запрещены сообщения).
- **`benchmark_queries.parquet`** — текст запроса, локация и строка фильтра.

**Признаки и зачем они:**
- **Похожесть текста** — по кусочкам слов, по леммам и по смыслу (нейросетевая модель). Запросы короткие, около 3 слов, и с опечатками, поэтому нужны и точные совпадения, и смысл. Описание объявления целиком вместо первых 300 символов дало +2,6 п.п., а без описания результат падает на 4,1 п.п.
- **Вероятность перехода «локация поиска → локация объявления»** — главный сигнал: без неё recall падает с 0,885 до 0,367. Простое равенство городов не годится: у 17% запросов в выбранной локации нет ни одного объявления.
- **Вероятность подкатегории** по похожим прошлым запросам: 86% кликов одного запроса приходятся на одну подкатегорию. Прирост +1,4 п.п.
- **Совпадение фильтра «Вид/Тип услуги» с параметрами объявления.** У выбранных объявлений значение фильтра есть в параметрах в 98% случаев. Прирост +0,7 п.п.
- **30 признаков ранкера:**
  - оценки и места кандидата в каждой из четырёх оценок, отрыв от лучшего кандидата пула;
  - вероятности локации и подкатегории, совпадение фильтра по каждому ключу;
  - та же ли это локация и расстояние до неё;
  - цена и флаги объявления;
  - свойства запроса: длина, есть ли фильтр, регион это или город, встречался ли текст раньше, насколько уверен прогноз подкатегории.

**Сознательно не используются:**
- **категория поиска:** 99% корпуса относится к одной категории, а «категория 0» есть у 9% тестовых запросов и лишь в 34 строках train;
- **признак доставки:** 12 строк в train и ни одного тестового запроса;
- **признаки прошлого успеха объявления** — популярность, отзывы, рейтинг, тексты прошлых запросов к нему. Они помогают только объявлениям, которые уже кликали, и на тесте прироста не дают (см. ниже).

### Какие модели и алгоритмы применены

- **TF-IDF** по символьным n-граммам (char_wb 3–5) и по леммам слов (1–2-граммы, pymorphy3), косинусная близость.
- **multilingual-e5-small**, дообученная как bi-encoder на парах «запрос → выбранное объявление». Лосс MNRL (in-batch negatives) плюс «трудные» негативы — объявления той же локации и подкатегории, 1 эпоха.
- **Приоры:**
  - матрица переходов между локациями, посчитанная по кликам;
  - kNN (k = 20) по TF-IDF текстов прошлых запросов — для подкатегории;
  - поиск подстроки «ключ значение» в параметрах объявления — для фильтра.
- **Линейная комбинация оценок** по всему корпусу на GPU, веса подобраны Optuna (TPE).
- **LightGBM LambdaRank** (150 деревьев) переранжирует пул примерно из 175 кандидатов — объединение top-100 четырёх оценок.

### Как проверялось качество до отправки

- **Валидация устроена как тест.** Из train отложены 6 500 поисков с полным контекстом:
  - 5 000 текстов удалены из train целиком — это новые запросы;
  - 1 500 — знакомые тексты в новом контексте.
  
  Всё, что обучается на train (вероятности, модель текста), считается только по оставшейся части, поэтому утечки нет.
- **Метрика — Recall@50**, взвешенный по четырём группам (знакомый или новый текст × есть или нет фильтра) в пропорциях теста. В каждой группе не меньше 570 запросов, для метрики считается стандартная ошибка.
- **Веса подбирались на одной половине валидации, а прирост проверялся на другой.** Ранкер оценивался перекрёстно (cross-fitting) по двум половинам запросов.
- **Порог принятия изменения** — прирост от 0,3 п.п. (для новых гипотез — от 0,5 п.п.). Если прирост меньше, остаётся более простой вариант.
- **Отдельно считается recall по объявлениям**, которые встречались и не встречались в train. Так виден прирост, который держится только на истории.
- **«Холодная» валидация** появилась после первых загрузок и откалибрована по лидерборду: прирост на ней переносится на тест на 50–60%.
- **Перед каждой загрузкой — проверка формата ответа:**
  - колонки `query_id,answer`;
  - все 2 452 запроса без дублей;
  - в строке от 1 до 50 уникальных id, и каждый есть в корпусе.

### Какие ошибки найдены и что с ними сделано

**Промахи модели (разбор валидации по группам запросов):**
- **Регионы-агрегаты.** Человек ищет «по области», а исполнители находятся в городе. Recall здесь 0,82 против 0,93 у городов. Сделано: матрица переходов вместо равенства локаций. Гео-сглаживание и отдельные веса для регионов дали только +0,3 п.п., это в пределах шума. Регионы остаются главным открытым местом.
- **20 самых частых локаций теста** (59% запросов — крупные города и регионы): recall 0,90 против 0,96 в остальных.
- **Нужное объявление далеко по тексту, но единственное рядом с пользователем.** Сделано: оценивается весь корпус, а не первые результаты текстового поиска. Поиск только внутри «своих» локаций оказался хуже — до −1,9 п.п.
- **Нужного объявления нет в пуле** у ~4% запросов, и ранкер это исправить не может. Пул из 200 кандидатов поднимает потолок до 98%, но итоговый прирост лишь +0,16 п.п., поэтому пул не расширен.
- **Новые тексты без фильтра** — самая слабая группа (0,910) и одновременно самая весомая: 47% теста.

**Ошибки в данных:**
- **Шум в параметрах объявлений** (график работы, тип стоимости, адрес) вычищен: +0,3 п.п.
- **Описание объявления обрезалось до 300 символов** — теперь берётся целиком: +2,6 п.п.
- **Фильтр — склеенные пары «ключ значение» без разделителей**, а у 2% строк перед ними ещё и нераспознанный текст. Сделано: строка разбирается по списку известных ключей.

**Ошибки оценки и процесса:**
- **Валидация завышала результат на 4–5 п.п.** У отложенных объявлений была история кликов, а до сих пор активные объявления раскручены: медиана отзывов у них 42 против 15. Сделано: «холодная» валидация и ранкер без признаков популярности и отзывов.
- **Доля запросов с фильтром в train и в тесте разная:** 67% против 37%. Сделано: группы перевзвешиваются по тесту.
- **Итоговый ранкер с ранним остановом останавливался на 17 деревьях вместо ~150.** Сделано: число деревьев фиксировано.
- **Два одинаковых запуска совпадали лишь на ~95%** из-за шума вычислений на видеокарте. Сделано: вычисления во float64 и детерминированная сортировка. Теперь ответ повторяется побайтово.

## Основные идеи

### 1. Сначала — валидация, которой можно верить

Разметки теста нет, а число попыток на лидерборде ограничено. Поэтому сначала строится локальная проверка, устроенная как тест. Из train откладываются поиски с полным контекстом (текст, город, фильтр) — так же, как устроен тестовый запрос. Часть отложенных текстов модель раньше не видела, часть — видела в других контекстах.

Итоговая метрика взвешивает эти группы в той же пропорции, что и в тесте. Это важно: фильтр есть у двух третей поисков в train, но лишь у трети тестовых запросов, и без перевзвешивания легко переоценить всё, что связано с фильтром.

### 2. Оценивать весь корпус, а не первые результаты текстового поиска

Нужное объявление может быть двухтысячным по тексту, но единственным в городе пользователя. Поэтому оценку получает каждое из 189 тысяч объявлений. Запросы обрабатываются пачками на видеокарте, и в памяти хранятся только лучшие кандидаты.

### 3. Локация — это переходы, а не совпадение

У 17% тестовых запросов в выбранной локации нет ни одного объявления: человек ищет «по области», а исполнители находятся в областном центре. Поэтому вместо проверки «тот же город или нет» используется вероятность перейти из локации поиска в локацию объявления, посчитанная по кликам.

### 4. Подкатегория и фильтр

По 20 самым похожим прошлым запросам решение определяет, в какие подкатегории обычно уходят клики: 86% кликов одного запроса приходятся на одну подкатегорию. Если в поиске выбран фильтр «Вид/Тип услуги», объявления с этим значением в параметрах получают бонус.

### 5. Текст: точные совпадения и смысл

Два способа сравнивать текст дополняют друг друга:
- **сравнение по кусочкам слов и леммам** устойчиво к опечаткам и склейкам;
- **нейросетевая модель multilingual-e5-small, дообученная на кликах из train**, улавливает смысл: связывает «сантехника» с «заменой смесителя».

При дообучении модели специально показывались «трудные» неправильные ответы — объявления из того же города и той же подкатегории. Так она учится различать именно близкие варианты. Ещё один заметный прирост дало то, что модель читает описание объявления, а не только заголовок и параметры.

### 6. Ранкер поверх пула

Пул составляется из лучших кандидатов по четырём оценкам. Нужное объявление попадает в него у 96% запросов. Модель LightGBM переставляет пул по 30 признакам — оценкам и позициям кандидата в каждой из четырёх оценок, вероятностям локации и подкатегории, расстоянию, цене — и отдаёт первые 50.

### 7. Урок лидерборда: не учиться на прошлом успехе

Первый ранкер показал 0,938 на валидации и только 0,891 на лидерборде. У разрыва нашлись две причины:
- **У отложенных для проверки объявлений есть прошлое.** Их уже кликали, и многие из них хорошо знакомы модели по истории. А в тесте, судя по результатам, нужные объявления в основном новые.
- **Активные до сих пор объявления раскручены:** медиана отзывов у них 42 против 15 по корпусу. Ранкер научился тянуть наверх популярное.

Решение:
- **«Холодная» валидация:** у проверочных объявлений стёрта вся история.
- **Ранкер без признаков популярности и отзывов.**

После этого прирост на валидации стал предсказуемо переноситься на лидерборд — примерно наполовину. Дальнейшие улучшения выбирались по холодной валидации, без загрузок вслепую.

## Проверенные гипотезы

Изменение входило в решение, только если давало прирост заметно больше шума валидации. Не вошли:

| гипотеза | что показала проверка |
|---|---|
| искать только внутри «своих» локаций | хуже полного перебора, до −1,9 п.п. |
| приписать объявлению тексты запросов, по которым его находили раньше | на холодной валидации вредит: у новых объявлений такой истории нет |
| сглаживать локации по расстоянию, отдельно настроить регионы | +0,3 п.п. — в пределах шума |
| переносить запросы на похожие объявления | от −0,1 до −1,2 п.п. |
| отдельная модель, оценивающая пару «запрос — объявление» целиком (cross-encoder) | +0,3 п.п. ценой больше часа вычислений |
| брать в пул 200 кандидатов вместо 100 | +0,16 п.п. — в пределах шума |

## Запуск

Нужны Linux, Python 3.12, видеокарта NVIDIA от 8 ГБ и 16 ГБ RAM.

```bash
bash scripts/install.sh            # окружение (нужна сеть)
bash scripts/download_models.sh   # базовые модели (нужна сеть, один раз)
# положить dataset.zip в data/raw/
bash scripts/run_all.sh --clean    # всё с нуля, офлайн -> answer.csv
```

Прогон с нуля занимает около 2 часов, почти всё время уходит на дообучение нейросетевой модели.

Готовые модели и финальный ответ лежат на [Google Drive](https://drive.google.com/drive/folders/1SR7BWIuiPESjcB3aI-q1jusWh7qcbkTk?usp=sharing). Нужно распаковать `avito-candgen_models_hf.tar.gz` и `avito-candgen_models_s10.tar.gz` из корня проекта (`tar -xzf <архив>`) и запустить `bash scripts/run_all.sh` без `--clean`. Ответ строится примерно за 5 минут и повторяется побайтово. Что лежит в каждом архиве — в [docs/TECHNICAL.md](docs/TECHNICAL.md), раздел «Архивы моделей».
